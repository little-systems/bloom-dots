# Phase 4: OSD and Notifications — Implementation Plan

**Status:** proposed for owner review, 2026-10-27. This document plans the work; it does not authorize a live notification-server handover.

**Goal:** add Bloom's left-edge volume and right-edge brightness OSD, per-app mixer, volume protection, top-right notification cards, Do Not Disturb, and a history panel in the notch. End with Bloom owning notifications while the rest of ii remains available.

**Base:** local `bloom-dots` `main` at `fe73d29` (Phase 3C merged, no push). Source of truth: `docs/specs/2026-10-25-bloom-shell-design.md` D14, §3.2–3.4, §4.1–4.2, §6 and §8; Bloom `src/Overlay.tsx`/`Overlay.css` for OSD motion and shape. The installed Quickshell QML type metadata is the API authority for this machine.

## Current machine and constraints

- The live Bloom shell runs from `~/.config/quickshell/bloom` → this checkout, with `notch` and `dock` enabled. ii (`qs -c ii`, PID observed as 1046 while planning) owns `org.freedesktop.Notifications`, the SNI watcher, and its own OSD. Re-read ownership and processes immediately before any handover.
- The live backlight is `intel_backlight`; `brightnessctl` is installed. Do not hard-code the output or device name: discover it and show an unavailable state on a machine without backlight hardware.
- Current ii volume binds use `wpctl` at 2% steps with a 150% command cap; ii's protection setting is **disabled** by default, with configured maximum jump 10% and maximum level 99%. Current ii brightness binds go through ii IPC with a `brightnessctl` fallback. The handover must update live binds only after the new paths are verified.
- `NotificationServer` has no `enabled` property in this machine's installed QML type metadata. ii creates it unconditionally in `~/.config/quickshell/ii/services/Notifications.qml`. A Bloom server can be tested on an isolated D-Bus now; the live switch requires a reversible ii-side opt-out or equivalent explicit owner-approved coordination. Starting a second server and hoping it wins is not an acceptance path.
- The settings schema already permits `osd` and `notifications` module names; both are currently absent from the live module list. Keep all implementation behind those flags. Tray and polkit ownership stay with ii for Phase 6.
- The live shell reloads its linked working tree. Implement in an isolated worktree or keep each save loadable. Do not edit `~/.config`, restart either shell, change keybinds, change real audio/brightness, or send real notifications during implementation without the owner's separate live-check approval. Do not push.

## Rulings for owner review

1. **Split the phase into 4A/4B/4C.** 4A builds OSD and protection; 4B builds the notification server, cards, and history under a disabled module; 4C is the owner-approved exclusive handover. Cost if wrong: extra review boundary, but it keeps the owner session functional while the server is developed.
2. **Volume protection starts opt-in.** Preserve ii's current disabled default, offer maximum step increase (10%) and level (99%) when enabled, and never clamp the initial PipeWire reading after login/resume. A user gesture through Bloom is subject to the same cap as an external `wpctl` change. Cost if wrong: users who expected protection by default must enable it; default-on could unexpectedly reduce legitimate output.
3. **Notification history is bounded local state.** Store at most 200 non-transient notifications as primitive text/app/time/urgency fields in `StateFile`; never persist QML action handles or raw image bytes. Live notification actions work only while their object exists. DND suppresses normal/low popups but retains history; critical popups still appear. Cost if wrong: the cap discards older history, and critical items may interrupt DND.
4. **One visible owner per notification.** In the handover, preserve ii's history file as a backup; do not pretend a live action handle survives a server switch. Hide ii's popup/history entry points after its server is disabled so they cannot show stale data. Revert the ii opt-out and disable Bloom's module if ownership or a notification round trip fails.
5. **No hardware action in automated tests.** Unit and offscreen integration use fake PipeWire/backlight seams and an isolated session D-Bus. The owner check uses a reversible, measured adjustment with baseline values recorded and restored. Cost if wrong: an environment-specific device issue appears only in the live check.

## Verification focus

- **Ownership:** before, during, and after the handover, `busctl --user status org.freedesktop.Notifications` identifies exactly one intended process. A notification sent during the test appears once, accepts an action, closes on timeout, and is present in Bloom history. ii continues to provide other Phase 5/6 surfaces.
- **Volume:** external `wpctl` changes and Bloom sliders update the OSD once; changes while muted do not unmute unexpectedly. Protection handles a sudden jump, 0%, cap boundary, sink replacement, suspend/resume, and the corrective change it writes itself without loops. Per-app streams use PipeWire node identity, not the display name.
- **Brightness:** monitor/device discovery and percent math work at 0/max; the OSD responds to Bloom's keybind path and a real external brightness change. No backlight device hides the slider cleanly. A failed `brightnessctl` call reports a bounded error without optimistic state drift.
- **Notifications:** replacement ID updates a card and history entry, close reason is reflected once, transient items never persist, timeouts respect `expireTimeout=0`, actions target only the live object, images and markup cannot execute commands or escape their display box, and restart reloads history without resurrecting popups.
- **Surfaces:** OSD pills are 42×196 before scale, flush to their respective edges and centred vertically, with the mixer attached to the volume pill. Cards stack top-right without covering the notch, fit 0.8–1.3 scale, and use tight input masks. Hidden surfaces draw zero frames after animations settle. Multiple screens keep state coherent without duplicate notification servers.

## Work sequence

### 4A — OSD, audio and brightness (nonexclusive)

1. **Settings and tokens.** Add typed OSD timeout, volume protection enable/max-jump/max-level, and notification settings (DND, timeout, history cap if configurable). Regenerate `docs/SETTINGS.md`. RED→GREEN schema tests cover invalid ranges and old string booleans; parity tests cover any new spring tokens. Done when schema/docs tests and `CI=true tests/run-all.sh` pass.
2. **Pure rules.** Add `shell/modules/osd/osd.js` for clamp, step/jump protection, startup/sink-change guards, percent calculation, timer/hold state and edge geometry. RED→GREEN tests cover all volume/brightness boundaries and corrective-write loop prevention. Done when focused tests cover each transition and the full suite passes.
3. **Audio and brightness services.** Extend `Audio.qml` to track the default sink and output streams, apply protection on external and Bloom changes, and expose mixer actions. Add a brightness service that discovers the backlight and uses argv-only `brightnessctl` calls; read back actual state after writes. Give tests injectable command/data seams. Done when fake-process integration proves exact argv, no real hardware mutation, and the full suite passes.
4. **OSD surfaces.** Add per-screen left/right `PanelWindow`s, shared `EdgeSurface` styling, 42×196 pills and a bounded four-column mixer. Open on meaningful state changes, close after timeout, keep input only on visible pill/mixer, and stop timers/animation at rest. Wire `shell.qml` only through `osd` LazyLoader. RED→GREEN component, geometry, interaction and idle-frame tests. Done when offscreen runtime integration shows module-off unchanged and module-on surfaces valid, then full suite passes.
5. **OSD live check.** After owner approval, snapshot real volume/mute/brightness and relevant binds. Enable the OSD briefly while ii remains running; verify visibility and read-only state reaction first. Test a small reversible volume/brightness change, restore exact baseline, and inspect logs. Decide with the owner whether ii OSD should be disabled at this stage; no keybind or ii edits in tasks 1–4.

### 4B — Notification server, cards and history (isolated until handover)

6. **Pure notification model.** Add ID/replacement, grouping, timeout, DND, unread and bounded-history rules. Keep live `Notification` objects outside persisted state. RED→GREEN tests for malformed hints/text, app grouping, duplicate IDs, transient, critical, action lifecycle and reload. Done when focused tests and the full suite pass.
7. **Service and state.** Add `Notifications.qml` with `NotificationServer` created only by a `notifications` LazyLoader. Preserve state through `StateFile` and serialize primitives only. Use the installed `Notification` action/dismiss API; report ownership failure rather than silently losing notifications. RED→GREEN isolated `dbus-run-session` integration uses `notify-send`/`gdbus` with a fake app to prove send, replace, action, close, DND and persistence. Done when live bus ownership is unchanged and the full suite passes.
8. **Cards and notch history.** Add top-right card surface and a notch history panel with explicit open/close IPC, unread count, clear/read actions, image fallback and accessible focus behavior. The card consumes pointer input only over cards. A history item whose live handle is gone has no action button. RED→GREEN component and interaction tests; full suite. Done when isolated shell can show and dismiss cards, reopen history after restart, and idle-frame tests settle.
9. **Fresh review.** Review the whole branch against the spec and this plan, including privacy, D-Bus ownership, notification loss, live action handles, multi-monitor placement and the ii rollback. Fix every Critical/Important finding with a failing focused test followed by the full suite. Done when both code and standards review are clean or remaining limitations are documented for owner decision.

### 4C — Owner-authorized exclusive handover

10. **Prepare the reversible switch.** Record current bus owner, ii/Bloom PIDs, binds, settings and ii files; back up every file to be touched. Implement and test the smallest ii opt-out for its `NotificationServer` and stale notification UI without disabling the rest of ii. Put a rollback script beside the handover notes and test it against a disposable copy. Done when the owner can review exact file diffs, commands, expected bus owners and rollback before the live switch.
11. **Switch once.** With explicit owner approval for the reviewed changes, disable ii's notification server, verify the name is unowned, enable Bloom's `notifications` module, verify Bloom alone owns it, then send action/replacement/timeout test notifications. Keep the other ii services active. On any failed check, disable Bloom's module and restore ii from backup immediately. Done when ownership and the notification round trip pass without duplicates, the history panel works, and the owner accepts the visible cards.
12. **Closeout.** Restore test audio/brightness values, remove temporary notifications, verify no stale ii UI or warnings, run the full suite, update AGC handoff/context, and locally merge the reviewed branch. Preserve owner settings and do not push. Done when main is clean, Bloom service active, one notification owner verified, and the ledger records all Rulings and measured results.

The owner must review and approve that exact live ii edit and the rollback after 4A/4B are implemented. Until then, Phase 4 code remains testable with its module disabled in the owner's session.
